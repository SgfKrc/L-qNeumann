> 题目：**面向「权重即计算」的大模型推理引擎——基于 llama.cpp 的电路执行器实现**

## 一、QwenPU 是什么

**QwenPU 是把一台 RISC-V 计算机编译进 Qwen3.5-4B 权重里的模型。**

模型共 46 层，全部装在普通 `transformers` 能加载的权重里：

| 层 | 是什么 | 怎么来的 |
|---|---|---|
| 0–12 | RV32IM CPU + VX 向量单元 | **编译器生成**（非训练） |
| 13 | kernel 加速器层 | 编译产物 |
| 14–45 | Qwen3.5-4B 的语言层 | 预训练权重 |

**它想做的事**：让语言模型**自己执行程序**——不是「调用外部工具」，而是 token 流里真的跑起一个 CPU。
已能跑 CRC32、排序、算术、小游戏。

## 二、QwenPU 的核心主张与现状

**核心主张：模型自己算，不依赖主机。**

这个主张成立的前提是两件事：**跑得动**（性能可用）和 **装得下**（能部署）。**QwenPU 这两件都没做到。**

### 问题 A：性能不可用（它跑通了，但慢到不能用）

| 指标 | 数字 |
|---|---:|
| chip 步（原始） | **830.6 μs/token** |
| 一个 story token | 53,000 trace token ≈ **16–19 秒** |
| 对比真 CPU | 慢 **6–8 个数量级** |

**根因已经量化**：访存占 **85%**、matmul 只占 **0.07%**。它不是「算得慢」，是「搬数据慢」——
每个乘加要配 4 次 4 字节随机读。

### 问题 B：无法部署（它存在，但装不下）

| 路径 | 大小 | 8 GB 显卡 | 31.6 GiB 内存 |
|---|---:|---|---|
| Triton + safetensors | **22.87 GiB** | ❌ | ⚠️ 加 activation 就爆 |
| llama.cpp + GGUF | 14.20 GiB | ✅ offload | ✅ mmap |

**QwenPU 的官方路径是 PyTorch/safetensors。这意味着它在消费级单机上「能验证、不能用」。**

### 问题 C：没有端到端验证（优化的是「孤岛指标」）

之前所有 chip 性能数字（830.6 → 204.5 μs）**都是 chip 层单独测的**。完整 46 层推理**从未在这台
机器上跑过**——因为 22.87 GiB 放不进显存和内存。

**所以没人知道「优化 chip 对端到端到底有没有用」。**

## 三、本项目要解决什么

**把 QwenPU 从「跑通的实验」变成「能部署的系统」。**

| 要解决 | 对应问题 | 怎么解 |
|---|---|---|
| **装得下** | 问题 B | GGUF（14.20 GiB）+ mmap + 分层 offload |
| **算得对** | 问题 B 的隐藏代价 | **单一数值实现**（全 llama.cpp），不跨框架 |
| **跑得完** | 问题 C | chip + Qwen 同进程，**首次跑通完整 46 层推理** |
| **快得可用** | 问题 A | 移植已有的访存优化（head 拆 CTA、load 交织、per-layer KS） |

## 四、为什么必须是 llama.cpp

**选择由两条独立证据决定：跨框架的数值差，以及 safetensors 在单机上的装载劣势。**

### 证据 1：跨框架的数值差消除不了

| 机制 | Triton | ggml |
|---|---|---|
| 归约顺序 | 按 lane 并行 | 按 warp 归约 |
| 中间精度 | 显式控制 | 算子内部 |
| atomic 累加 | 顺序无关 | 依赖实现 |

**权重逐字节相同，结果也会在最后几位不同。** 而电路对数值是**位级敏感**的——bf16 ballast（2^40）
一旦舍入，电路就「看不见」那条线。**不是精度差，是算错。**

### 证据 2：safetensors 在单机上赢不过 ggml

| 维度 | safetensors + PyTorch | GGUF + ggml |
|---|---|---|
| 加载 | 全量进 RAM | **mmap 按需缺页** |
| 显存 | 显式 `to(device)` 全量 | **按层 offload** |
| 启动 | 秒级 22.87 GiB | 毫秒级 mmap |

**22.87 GiB 在 8 GB / 31.6 GiB 上跑不起来——这是生态问题，不是优化问题。**

### 证据 3：K-Llama v1 已经用 27,825 行买过这个教训

K-Llama v1 做过「PyTorch 段 + llama.cpp 段」的跨框架接力，结局记录在仓库里：

> **不是技术不可行，是产品决策放弃的**。F12 多模态/跨框架/PyTorch = **27,825 行（21.5%）**，
> 处置**抛弃**。

**所以本项目不做跨框架，全 llama.cpp。**

## 五、立项逻辑链

> QwenPU 证明了「权重里能装一台计算机」，但它**只能验证、不能部署**（22.87 GiB 装不下），
> **只能跑通、不能使用**（慢 6–8 个数量级），**只测了孤岛、没跑过端到端**。
>
> 本项目在 llama.cpp 里实现电路执行器，**用单一数值实现保证正确性、用 GGUF+mmap 保证可部署、
> 用同进程串接保证端到端**，并把已有的访存优化移植过来。
>
> 它补齐的不是「又一个优化」，而是 **QwenPU 从实验走向系统的缺失环节**。

## 六、需求（软件工程口径）

### 功能性需求

| # | 需求 | 来源 |
|---|---|---|
| F1 | 在 llama.cpp 中执行编译进权重的电路层（13 层 RV32IM + 1 层 kernel） | QwenPU 模型结构 |
| F2 | 保持与黄金参考（IR `evaluate`）位精确一致 | 电路的 pinned-constant 契约 |
| F3 | 支持完整 46 层推理（电路 + Qwen 语言层，同一进程） | 端到端可用性 |
| F4 | 复用 llama.cpp 的 GGUF 加载、mmap、分层 offload | 单机资源约束 |

### 非功能性需求

| # | 需求 | 约束值 |
|---|---|---|
| N1 | **可部署性** | 8 GB 显存 + 31.6 GiB 内存单机能跑（14.20 GiB GGUF） |
| N2 | **正确性** | 对 IR 逐位一致（不是「差不多」） |
| N3 | **性能** | chip 步 ≤ 150 μs（参考基线见 [BASELINES](../measure/BASELINES.md)） |
| N4 | **可维护性** | 单一数值实现，零 PyTorch 依赖 |
| N5 | **可验证性** | 有自动化验收（对 golden trace / IR） |

## 八、不做什么（边界）

| 不做 | 理由 |
|---|---|
| 跨框架（PyTorch ↔ llama.cpp） | 数值差消除不了；K-Llama v1 用 27,825 行证明过 |
| 新硬件设备（AES/SHA/zlib） | token 带宽 15–16 bit 是硬墙，装什么都喂不饱 |
| 流水线（IF/ID/EX/MEM/WB） | 分支率 26.5%，实测负收益 |
| persistent kernel | 实测 1.017×，阶段 2 会慢 14% |
| 训练 | 全程无训练（这是 QwenPU 的前提） |
