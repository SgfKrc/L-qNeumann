# 视觉塔除了「图像输入」还能做什么

> 状态：**调研报告（旁路形态已决）**
> 更新日期：2026-11-22
>
> 适用范围：视觉塔在 rv1 里能做什么、旁路形态的实测与边界；读者为决定要不要做视觉扩展的人。
> 相关：[ARCHITECTURE](ARCHITECTURE.md)（视觉塔旁路一节）、[PLAN](PLAN.md)。

## 0. 结论

1. **五个方向里只有一个真的值得做：把视觉塔当成电路板的「模数转换器」**（图像 → 离散整数 → 电路），
   而不是「模态桥」（图像 → 残差流 → Qwen）。前者零权重改动、毫秒级、实测读数 99–100%；
   后者在 8 GB 上要跑 576 token × 32 层，是百秒级，且要重新验证 overlay。
2. **用户的前提「image token 走 OTHER 类」只在 q35 里成立；rv1（当前主线）里视觉塔被整份丢弃**
   （`rv/merge.py:239-240`）。所以「视觉塔还能做什么」的第一件事不是加能力，是**决定要不要它**。
3. **电路侧已经有全部需要的接口**：文本捕获窗口 + 2 KB 文本缓冲（RAM）+ 394 K 的 chip 词表 + `value_record` 编码。
   缺的只有视觉前端。这是整件事成本低的原因。
4. 实测给出三条硬数字：视觉塔独立加载 636 MiB / 前向 256 px 28.8 ms、768 px 129.6 ms / 峰值 747 MiB；
   冻结塔 + 线性头：单数字跨字体 100%，2×2 表格 4 格全对 85%（跨字体 75%），3 位数 98.9%，
   加数据增强后噪声/模糊/±5° 旋转全 100%；同图两次前向差 2.9e-6。

`<|image_pad|>` 的 14 字节。这就是为什么「往 rv1 里塞 image token」不是「无害」，而是「可能污染 tool_call 捕获」。

## 2. 五个方向的评估

### 方向 1：图像 → 电路（最直接）— **可行，但接口要选对，实测支持**

拆成两个子问题。

**(1a) 2560 维怎么变成 chip token？** 三条路：

| 路 | 做法 | 可行性 | 评价 |
|---|---|---|---|
| A. 离散读数头 | 冻结塔 → 线性/MLP 头 → 数字/字符 → **数字字符文本 token** | **实测 99–100%** | 复用现成捕获通道，零 merge 改动。推荐起步 |
| B. 整数 → F0 | 读数头拼成整数 v → `spec.value_record(v)` → 1 个 F0 token（15 bit） | 编码现成（`value_record`），但电路缺「读值记录」的入口 | 单 token 表达整个数，更适合 kernel/MMIO；需要新接口 |
| C. 直接回归 15 bit | 2560 → 线性 → 量化到 payload | 不推荐 | 视觉特征是连续的，强行当二进制位用；量化误差 + 需要量化训练，误差不可控 |
| D. 不转 token，走残差 | image token 行 = 视觉特征，Qwen 读 | 可行但慢（见 1c） | 不是「图像→电路」，是「图像→Qwen」 |

实测（`_vt_digits.py`、`_vt_table.py`、`_vt_num.py`、`_vt_aug.py`，冻结塔 + 线性头，合成印刷数字）：

| 任务 | 同分布 | 跨字体 | 备注 |
|---|---|---|---|
| 单数字 0–9（8 字体 × 30 张） | 100% | **100%** | 类均值余弦最大 0.918，仍线性可分 |
| 2×2 表格，4 数字全对 | **85.0%** | **75.0%** | 单格 87.5–96.2% |
| 3 位数（1 开头），全对 | **98.9%** | — | 单数字 98.9–100% |
| 3 位数 + 高斯噪声（σ=40） | 100%（增强训练） | — | 不增强只有 61.7% |
| 3 位数 + 1.5 px 模糊 | 100%（增强训练） | — | 不增强 **0%** |
| 3 位数 + ±5° 旋转 | 100%（增强训练） | — | 不增强 13.3% |

**结论：路 A 是真的能用的，不是「理论上能做」**——但有一个必须写进设计的性质：**冻结塔对分布外输入极脆**
（模糊 0%、旋转 13%），必须带数据增强训练，且必须在部署时用同一套预处理。

**(1b) 需要什么接口改动？** 两条，成本差一个数量级：

- **旁路（推荐）**：host 侧加载 636 MiB 视觉塔 + 读数头 → 输出数字字符 → 作为**普通文本 token** 拼进 prompt
  （和 `docs/running.md` 里 BIOS boot tokens 完全同一机制）。电路侧 0 行改动：
  `<tool_call>` 捕获把文本写进 `TEXT_ADDR` 缓冲（已实现），calc 固件解析表达式并精确计算，结果以 BYTE token 输出。
  **代价：0 行 merge、0 行电路、0 行 IR。**
- **残差（1c）**：改 merge 保留 visual（约 30 行：去掉 `continue`、config 换 `Qwen3_5ForConditionalGeneration`
  结构、merger 的 `OUT_ROWS` 加宽会自动生效）→ image token 行的前 2560 放视觉输出、后 2048 清 0/填 OTHER。
  加 `chat.py` 的像素输入路径（约 80 行）。**要重测 overlay**（见方向 4）。**8 GB 上慢两个数量级。**

**(1c) 8 GB 上的时间账（这是决定性的一点）**：

| 路径 | 计算量 | 实测/估计 |
|---|---|---|
| 视觉塔单独前向（768 px，576 token） | 0.336 B 参数 × 576 token | **实测 129.6 ms** |
| 576 个 image token 过 Qwen 32 层 | 576 × 4 B 参数 | 8 GB 下 Qwen 层在 CPU（`chip_only`）→ **约 100 s 量级**；即使全在 GPU 也要秒级 |
| 1 个 chip token（电路） | — | 实测 204.5 μs |

所以「图像进视觉塔、但**不进 Qwen 的 token 序列**」是 8 GB 下唯一有意义的形态。这也是方向 1 的真正价值：
不是「让 Qwen 看见图」，而是「让电路看见数」。

**障碍清单**：
1. rv1 没有视觉塔（要先决定恢复还是旁路）。
2. 读数错误率（实测 0–2.8%）对「验算」用例是致命的：验算的目的就是消除错误，1% 的读数错误会污染整条链。
3. 768×768 上限（48×48 patch 位置网格）→ 高分辨率文档要切片，成本线性增长。
4. 我只测了合成印刷体 + 简单布局；照片、透视、手写、低对比度未测。

### 方向 2：视觉塔作为「通用编码器」（非图像数据排成 2D）— **不建议，是误用**

它为什么不是通用编码器，有四条硬约束（都能从权重/配置直接读出来，不是猜）：

1. `patch_embed.proj.weight` 形状 **[1024, 3, 2, 16, 16]**：3 通道、2 帧、16×16 像素。
2. `pos_embed` [2304, 1024] 是 **48×48 的固定 2D 网格**，插值到每张图的网格——它编码的是「图像上的空间位置」。
3. `preprocessor_config.json` 的 mean/std 都是 0.5（自然图像统计）。
4. 输出经 `merger` 到 2560 维——**这是与 Qwen 语言空间对齐的语义空间**，不是数值空间。

所以「对非图像数据有意义的概率」我的判断：
- **把数据画成图再编码**（频谱图、热力图、散点图、矩阵可视化）：**有意义**，因为那本来就是图像，这条路和方向 1 是同一件事。
- **把非图像数据直接塞进 patch 网格**（时间序列变 1×N、矩阵当像素、图结构当邻接矩阵）：**低于 10%** 能做到比手工特征好，
  高层语义基本无效（它没见过这种统计）。
- 而且主板里更便宜：kernel 插槽是 64×64 matvec、VX 是 64-lane，都是精确的；用 636 MiB 的不精确近似去编码矩阵没有道理。

**「误用编码器」吗？是。** 但有一个正当版本：把数据**渲染成图**（图表、频谱图、矩阵热图）再让视觉塔读——
那已经不是误用，而是「渲染 → 视觉读数」的合理闭环，归到方向 1。

---

### 方向 3：视觉塔 + 电路做「感知计算」闭环 — **现阶段价值最低**

现状确认：架构是 **视觉 → 残差流 → 语言**，没有「视觉 → 电路」。要建闭环，缺的是**半个执行器**：

| 环节 | 现状 | 缺什么 |
|---|---|---|
| 电路 → 图案 | 电路只能写 RAM（32 KB，`spec.py:92`）与文本缓冲（2 KB） | 没有像素输出通道；要 host 在 token 间把 RAM 导出、reshape 成帧，再喂视觉塔 |
| 视觉塔 → 特征 | 有 | — |
| 特征 → 电路 | 同方向 1 | 离散化 |
| 闭环收益 | 无证据 | 电路自己知道它算的值，绕一圈不会得到新信息 |

**「电路画图 → 视觉塔看 → 电路」在功能上是冗余的**：它把电路已经知道的数重新测一遍。
唯一可能有意义的变体是「外部图像 → 电路决策 → 改变外部状态 → 再看」（机器人 / UI 自动化），
但主板没有执行器——电路的输出只能回到 token 流，无法改变外部世界，闭环缺一半。

「要改吗？」**不要改成双向闭环。** 正确关系是单向：视觉 = 输入设备（ADC），电路 = 计算设备。
`ARCHITECTURE.md` 自己写的就是「VISION：输入设备（不是计算设备）」，这句话是对的，方向 3 建议违背了它。

### 方向 4：视觉塔作为「多模态接口」（Qwen 原生 VLM 能力）— **rv1 已破坏；q35 保留但只是「通道」**

**答案：在 rv1 里被破坏，不是被保留。**

- rv1：`merge.py:239-240` 直接跳过 `model.visual.*` → 产物是 `Qwen3_5ForCausalLM`，无 `vision_config`，
  dist 里 0 个 visual key。所以 rv1 **不能看图**，任何 image token 只是被当文本。
- q35：保留 636 MiB，且 image token 走 OTHER 类（`q35/merge.py:265-269`）——Qwen 能看图、电路静默。
  但注意这个「静默」只处理了 **chip 段**（merger bias 的后半），**没有处理 overlay 的那 1273 个共享 slot**。

**chip token 和 image token 怎么共存**——三层，代价递增：

| 层 | 做法 | 成本 | 风险 |
|---|---|---|---|
| L1 并列 | image token 只走 Qwen 路径，chip token 只走电路路径，二者不共享列 | 低（就是 q35 现状） | 8 GB 下 576 token × 32 层 = 百秒级，实际不可用 |
| L2 静默 | 让 image token 在电路侧等价于一个确定的「非 token」 | 中：要定语义（chip 段填 0 = PAD？还是 OTHER？两者后果不同） | `core.py:163` 会把它当 is_text=1，进捕获窗口 |
| L3 精确 | 保证 overlay 三条件在 image token 上成立 | 高：必须扩 `corpus()` 覆盖 image token、用真实视觉特征填行、重测并重 pin | 未测过；`overlay.py` 的精确性是「在 corpus 覆盖范围内」成立的 |

所以「多模态能力被保留还是破坏」的准确答案是：**q35 保住了 L1，rv1 一个都没保住；L2/L3 两个线都没有做。**

### 方向 5（自选）：把视觉塔定义为「视觉 ADC」——第五插槽的正式接口

这是我认为真正的新方向，也是方向 1 的工程化形态。

**主张**：视觉塔在主板里的正确身份不是「多模态入口」，而是**一个输入设备**——像 VX 是一个计算设备那样。
它的接口应该是一句话：

```
VREAD(region) -> 整数 v        # 一次前向：图像 → 15-bit 整数 → 电路
```

三个设计要点，每一个都能对上现成机制：

1. **输出必须是离散整数，不是连续特征**。因为电路的契约是 bf16-exact（`check_bf16`、`tiny.code_gain`），
   任何连续量进电路都要先量化；量化在**进入 token 流之前**做完，就不会碰电路的精确性契约。
   这也是路 A（分类头）优于路 C（回归）的原因：分类的结果天生是整数。
2. **带宽刚好够**：F0 家族 32768 个 payload = 15 bit = 一个 0–9999 的四位数，一条记录一个 token
   （`spec.py:137` 的 `value_record` 按大小自动选 F0/F1/F2）。「读一个表格单元格」= 1 次塔前向 + 1 个 token。
3. **通道可以复用现成的**：数字字符走 P3 文本捕获 → 2 KB 文本缓冲（`core.py:989`）→ 固件读；
   或整数走 F0 token → 需要一条「读值记录」的入口（这就是 P4「图像 token 能触发一个 kernel」要补的那一块）。

**这个方向和方向 1 的区别**：方向 1 是「让图像信息进到电路」，方向 5 是「把这件事做成第六个插槽的接口」——
也就是把 `mainboard-architecture.md` 的 P4 从「通道通了」推进到「语义 + op 定义」。P4 的验收标准
（「图像 token 能触发一个 kernel」）其实已经假定了这条路。

对比 `ARCHITECTURE.md` 的四维资源：视觉读数**不占残差列**（只在 host 侧算）、**不占层**（不进 Qwen 栈）、
**占 1 个 token 的时间**（F0 值记录）、**不占状态**。这是五插槽里最便宜的一种。

## 3. 最推荐的 1 个

**方向 1 的「旁路」路径 = 方向 5 的落地形态：host 侧视觉塔 + 读数头 → 文本/chip token → 电路。**

具体形态：

```
图像 ──PIL resize/归一化──▶ 视觉塔(636 MiB, 冻结) ──▶ 读数头(线性/浅 MLP)
                                                        │
                                          "123"（数字字符）或 F0(123)（15-bit 整数）
                                                        │
                        ┌───────────────────────────────┘
                        ▼
        普通文本 token / chip token 进 token 流（prefill 阶段，如 BIOS boot）
                        ▼
        电路：P3 文本捕获 → TEXT_ADDR 缓冲 → calc 固件解析 → 精确计算 → BYTE 输出
```

**理由（按权重排）**：

1. **零压缩成本**：0 行 merge、0 行电路、0 行 IR 改动。所有需要的东西都已经在仓库里
   （文本捕获、文本缓冲、`value_record`、chip 词表 394 K、boot token 注入的先例）。
2. **8 GB 上唯一跑得动的形态**：视觉塔 747 MiB 峰值 + 130 ms/图，对比 576 token 走 Qwen 的百秒级。
   这不是优化，是可行性问题。
3. **实测已经跑通能力**：跨字体单数字 100%、3 位数 98.9%、增强后噪声/模糊/旋转 100%（见 §2 表）。
4. **能力互补而非重叠**：视觉塔强在「读」（93.1% 的图表事实判断），弱在「算」；电路算 100% 精确。
   外部证据：Qwen3-VL-4B base 在 FinChart-Bench 的 QA 只有 31.6%（多步计算），TF 却有 93.1%
   （[FinChart-VL-4B](https://huggingface.co/varadsrivastava/FinChart-VL-4B)、
   [Seeing and Solving Are Not Enough](https://arxiv-org.ezproxy.obspm.fr/html/2609.33694v1)）。
   也就是说「读得准、算不准」是 VLM 的系统性弱点，而电路正好补这一半。
5. **不碰 overlay**：读数在 host 侧完成，电路只收到一个 token，不存在「新 token 类型破坏 pinned-constant」的问题。

**不推荐的替代（方向 4 的 L1/L3）**：保留原生 VLM 让 image token 走残差。技术上优雅（stock 架构、零训练），
但（a）8 GB 下 576 token 的 prefill 是百秒级，实际不可用；（b）要重新验证 overlay 三条件；
（c）它解决的是「Qwen 看图」，不是「用户问的视觉塔还能做什么」——Qwen 本来就会看图，加回视觉塔只是恢复退化。

## 6. 没想清楚的

1. **读数错误率怎么处理**。验算用例的核心价值就是「消除错误」，1% 的读数错误会让整条链失效。
   现在的线性头没有置信度。需要「拒读/低置信度转人工」的机制，而这会改变交互协议。
2. **真实图像的落差有多大**。我只测了合成印刷体。照片、透视、手写、低分辨率监控画面——一个都没测。
   不增强时 1.5 px 模糊就从 100% 掉到 0%，这个脆性足以推翻「开箱可用」的假设。
3. **image token 走残差时电路是否真的静默**。`core.py:163` 会把它判成文本；`q35/merge.py` 只补了 chip 段
   没补 overlay 的 1273 个 slot。这条路径的安全性**没有测过**，不能写成「已验证」。
4. **8 GB 上 rv1 常驻 + 视觉塔同存是否够**。我只测了视觉塔单独（747 MiB 峰值）。`chip_only` 模式下
   chip 层 + embedding 已经在 GPU 上，再加 747 MiB 会不会爆，需要实测。
5. **「视觉塔留在 checkpoint 里」还是「host 旁路」**。旁路更省、更灵活，但违背「主板是一个模型」的设计原则
   （D1：单一 checkpoint）。这是个架构取舍，不是技术问题，需要拍板。
6. **768×768 的上限**。高分辨率文档要么切片（成本线性涨），要么外推位置编码（风险未知）。
   位置网格是 48×48 固定的，`num_position_embeddings=2304` 硬编码在权重里。
